앞선 글들은 편하게 '데이터가 있다'고 가정했다. [씬](/posts/av-scene-data)이 있고, [좌표계](/posts/av-3d-geometry)가 맞춰져 있고, 그 위에서 모델이 돈다고. 하지만 실무의 절반은 그 앞 질문이다. **주행 한 번은 어떤 파일로 기록되고, 페타바이트 속에서 지금 필요한 장면을 어떻게 꺼내는가.** 여기가 '자율주행 데이터 엔지니어'라는 말의 본진이다.

## 원본 로그의 성질

한 번의 주행은 여러 센서가 서로 다른 주기로 쏟아내는 **시간순 메시지 스트림**이다. 20Hz 라이다, 30Hz 카메라 ×N, 100Hz IMU, GNSS, CAN… 이걸 한 파일에 시간순으로 적으면 그게 **로그(log)** 다. 성질이 까다롭다.

- **멀티모달** — 한 파일에 종류가 다른 메시지가 섞인다.
- **고빈도·대용량** — 몇 분이 수 GB, 하루가 수 TB.
- **시간이 1급 시민** — "그 순간"으로 되감아 재생(replay)할 수 있어야 한다.

## rosbag — 고전

먼저 **ROS 1의 rosbag 파일 형식**과 **ROS 2의 rosbag2 기록 도구**를 구분해야 한다. ROS 1 bag에도 청크와 인덱스가 있다. ROS 2 rosbag2는 저장 플러그인을 통해 SQLite나 MCAP 등을 사용할 수 있으므로 'rosbag에는 인덱스가 없고 MCAP으로 바꿔야 한다'는 비교는 맞지 않는다. 실제 선택은 사용하는 메시지 인코딩, 압축, 시간 구간 읽기, 기존 도구와의 호환성을 기준으로 한다.

## MCAP — 범용 로그 컨테이너

ROS 안팎에서 사용할 수 있는 컨테이너 중 하나가 **MCAP**이다. 한 줄로 말하면 "**어떤 메시지든** 담고, **빠르게 되감고**, **자기 자신을 설명하는** 로그 파일".

- **스키마 불가지(schema-agnostic)** — ROS 메시지든 **Protobuf**든 JSON이든, 채널마다 스키마를 함께 박아 담는다. 그래서 **self-describing** — 파일만 있으면 무엇이 들었는지 안다.
- **선택적인 인덱싱 + seek** — 요약·청크 인덱스를 기록하면 원하는 토픽과 시각을 찾아 필요한 구간만 읽을 수 있다. 모든 MCAP 파일이 인덱스를 포함하는 것은 아니다.
- **멀티모달·압축·append 친화**. ROS에 안 묶인다.

MCAP은 Foxglove가 개발한 공개 포맷이며, rosbag2와 [시각화 도구](/posts/av-visualization)에서 활용할 수 있다. 프로젝트의 기록·복구·읽기 요구를 검증한 뒤 채택하는 것이 좋다.

여기서는 개요만 짚는다. 파일 안쪽 구조, 스키마 선택, 세 개의 시계, 인지·융합·계획·제어의 토픽 설계, 실제 마이그레이션 절차는 [MCAP 완전 정복](/posts/av-mcap)에서 따로 판다. **회사 로그 포맷을 실제로 MCAP으로 바꾸는 중이라면 그쪽이 본편이다.**

## 두 층위: 기록용 vs 분석용

여기서 실무의 핵심 설계가 나온다. **하나의 포맷으로 다 하려 하지 마라.** 로그 데이터는 성격이 다른 두 일에 쓰인다.

| | 기록·재생 | 분석·학습 |
| --- | --- | --- |
| 접근 | 시간순, 한 로그 통째 replay | "밤·좌회전·보행자" 조건으로 가로질러 |
| 포맷 | **MCAP**(행/시간 정렬) | **컬럼형 Parquet**(질의 정렬) |
| 최적화 | 빠른 seek·멀티모달 | 열 프루닝·조건 필터·집계 |

페타바이트 MCAP을 매번 뒤져 "밤에 좌회전한 장면"을 찾을 수는 없다. 그래서 **MCAP → 필요한 신호를 뽑아 컬럼형(Parquet) 레이크하우스로 굽고**, 그 위에서 질의한다. record는 MCAP, analytics는 Parquet — 이 2층이 현대 AV 데이터 스택의 뼈대다.

## 변환 골격: 캡처 시각을 맞춘 뒤 Parquet으로 굽기

MCAP에서 라이다와 에고 포즈를 읽어, [좌표 변환](/posts/av-3d-geometry)으로 점을 월드로 옮기고 프레임 메타를 Parquet으로 쓴다. 아래는 **스키마별 어댑터를 생략한 설계 예시이며 그대로 실행되는 완성 스크립트는 아니다.** 핵심은 마지막으로 도착한 포즈를 재사용하지 않고, 모든 입력을 공통 시간축에 정합한 뒤 센서 캡처 시각의 포즈를 조회하는 것이다.

헬퍼 함수에는 다음 계약이 필요하다.

- `decode(schema, encoding, data)`는 채널의 스키마와 인코딩에 맞는 객체를 반환한다.
- `capture_time_ns(msg)`는 센서별 시계를 보정한 공통 시간축의 캡처 시각을 반환한다. `log_time`으로 대체하지 않는다.
- `PoseTimeline.from_samples(samples)`는 포즈 캡처 시각으로 정렬하고, 중복·불연속·유효하지 않은 자세를 검사한다. `interpolate(t, max_gap_ns=...)`는 구간 밖 외삽을 거부하며, 양쪽 포즈 간격이 한도를 넘으면 실패한다. 이동은 선형 보간하고 정규화한 쿼터니언은 SLERP한다.
- `calibration_at(t)`는 해당 차량·센서·시각에 유효한 버전의 `T_lidar_to_ego`를 반환하며, 불확실한 버전은 실패 처리한다.
- `to_reference_xyz(msg)`는 스윕의 점들을 지정한 캡처 기준 시각의 라이다 프레임으로 맞춘 점군을 반환한다. 이를 위해 필요하면 [점별 디스큐](/posts/av-deskew)를 수행한다. 포즈 보간 하나만으로 스윕 전체의 시간 왜곡이 해결되지는 않는다.

```python
from mcap.reader import make_reader
import numpy as np
import pyarrow as pa
import pyarrow.parquet as pq

# decode, capture_time_ns, PoseTimeline, calibration_at,
# to_reference_xyz는 위 계약을 만족하는 프로젝트별 어댑터다.
path = "drive_0042.mcap"
pose_samples = []
with open(path, "rb") as f:
    for schema, channel, message in make_reader(f).iter_messages(topics=["/ego_pose"]):
        msg = decode(schema, channel.message_encoding, message.data)
        pose_samples.append((capture_time_ns(msg), msg.position, msg.orientation_quat))
poses = PoseTimeline.from_samples(pose_samples)

rows = []
with open(path, "rb") as f:
    for schema, channel, message in make_reader(f).iter_messages(topics=["/lidar/points"]):
        msg = decode(schema, channel.message_encoding, message.data)
        t_ns = capture_time_ns(msg)
        # 50ms는 예시 정책값. 실제 포즈 주기·운동 오차 예산으로 정해야 한다.
        T_ego_to_world = poses.interpolate(t_ns, max_gap_ns=50_000_000)
        T_lidar_to_ego, calib_version = calibration_at(t_ns)
        pts = to_reference_xyz(msg)
        pts = pts[np.isfinite(pts).all(axis=1)]
        if not len(pts):
            continue
        pts_h = np.c_[pts, np.ones(len(pts))]
        world = (T_ego_to_world @ T_lidar_to_ego @ pts_h.T).T[:, :3]
        rows.append({
            "log_id": "drive_0042",
            "capture_time_ns": t_ns,
            "log_time_ns": message.log_time,  # 별도 보존: 기록 지연·탐색용
            "calibration_version": calib_version,
            "n_points": len(pts),
            "x_center": float(world[:, 0].mean()),
            "y_center": float(world[:, 1].mean()),
        })

if rows:
    pq.write_to_dataset(
        pa.Table.from_pylist(rows),
        root_path="lake/frames",
        partition_cols=["log_id"],
    )
```

이 예시는 작은 로그를 두 번 읽고 결과를 메모리에 모은다. 운영에서는 포즈 인덱스·청크 배치 처리·멱등적인 결과 커밋을 사용하고, 시간·캘리브레이션 검증 실패는 이유와 함께 격리 큐로 보낸다. 로그 ID별 파티션도 파일 수가 과도해지지 않는지 점검해야 한다.

핵심은 코드의 화려함이 아니라 **흐름**이다. `MCAP(원본 스트림) → 좌표 변환 → 필요한 신호만 컬럼으로 → 파티션된 Parquet`. 원본 점군은 그대로 두고, 질의에 쓸 **파생 신호와 메타만** 컬럼형으로 뽑는다.

## 페타바이트에서 장면을 꺼내는 법

컬럼형으로 구우면 비로소 '큐레이션'이 가능해진다.

- **파티셔닝** — `log_id`·날짜·시나리오로 잘라, 질의가 필요한 조각만 읽게.
- **공간 인덱스** — 세상을 타일로 나눠 위치 기반 조회(이 지점을 지난 모든 주행).
- **파생 태그** — 날씨·시간대·기동(좌회전/급제동)·객체 유무를 컬럼으로 미리 계산.

그러면 "비 오는 밤, 좌회전 중, 보행자 있음"이 **SQL 한 줄**이 된다. 롱테일 장면을 골라 [검출](/posts/av-3d-object-detection)·[점유](/posts/av-occupancy) 라벨링으로 보내는 데이터 플라이휠의 엔진이 이것이다.

## 재현성: 데이터도 버전이 있다

마지막으로 실무의 성숙도를 가르는 것. **어떤 데이터 버전이 어떤 모델을 학습시켰는가**를 추적하지 못하면, 성능 회귀의 원인을 영영 못 찾는다. 그래서 데이터셋 스냅샷을 **DVC·lakeFS** 같은 도구로 버전 관리하고, "모델 v7 = 데이터 스냅샷 2026-07-01 + 캘리브레이션 버전 x"처럼 못 박는다. [캘리브레이션이 씬을 따라다니는 메타데이터](/posts/av-calibration)라고 했던 이유가 여기서 완성된다.

## 정리

- 주행은 멀티모달·고빈도·시간순 **로그 스트림**으로 기록된다.
- **ROS 1 bag 포맷과 ROS 2 rosbag2 도구를 구분**한다. rosbag2에서도 MCAP을 저장 포맷으로 사용할 수 있다.
- **record는 MCAP, analytics/학습은 컬럼형(Parquet)** 으로 나누는 2층 구조가 핵심 설계다.
- MCAP을 읽어 좌표 변환 후 파생 신호를 파티션된 Parquet으로 구우면, 페타바이트에서 장면을 **질의로** 꺼낼 수 있다.
- 데이터 버저닝(DVC/lakeFS)으로 "어떤 데이터가 어떤 모델을 만들었는지"를 못 박아야 재현성이 선다.

그리고 이 2층을 실제로 어떤 인프라 위에 올리는가 — 저장 계층화, 레이크하우스, 학습 I/O — 는 [AV 데이터 플랫폼](/posts/av-data-platform)에서 이어진다.

이렇게 쌓아둔 로그는 보관용이 아니다. 관련 글에서 이 로그를 **다시 돌려** 모델을 검증하는 이야기 — [시뮬레이션과 리시뮬](/posts/av-simulation)로 간다.
